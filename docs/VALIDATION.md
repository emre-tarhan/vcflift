# Validation strategy

VCF Lift does not treat another liftover program's output as biological ground truth. Correctness is built around source/target reference invariants, allele-aware liftover, known fixtures, and differential testing.

## Runtime invariants

Every ordinary VCF production conversion must satisfy:

1. input parses successfully;
2. source chromosome names are normalized when necessary;
3. source REF alleles validate against hg38;
4. BCFtools/liftover performs coordinate + allele transformation;
5. destination REF alleles validate against hg19;
6. output is sorted, BGZF-compressed, and TBI-indexed;
7. rejected records are counted and optionally retained;
8. the exact engine/resource provenance is written to JSON.

A target REF mismatch is a hard failure.

For GATK-style gVCF, the default path adds these invariants before liftover:

1. source gVCF is staged against the verified hg38 FASTA;
2. `.fai` and `.dict` are available for the same source reference;
3. GenotypeGVCFs succeeds on the source assembly;
4. the resulting ordinary hg38 VCF again passes REF validation.

## DeepVariant gVCF validation

For a detected DeepVariant gVCF, VCF Lift treats the caller's non-reference genotype calls as the source variant callset. Before liftover, the extraction stage must:

1. retain every finalized record with `GT="alt"`, without restricting BCFtools variant type;
2. trim unseen `<*>`/`<NON_REF>` placeholder alleles and dependent Number=A/G/R values using BCFtools;
3. exclude `RefCall` (`0/0`) and `NoCall` (`./.`) records from the variant-only target artifact;
4. validate the remaining REF alleles against hg38 before liftover.

QC records the complete source `GT="alt"` count and the candidate set presented to liftover. Candidate conservation compares that independently counted source non-reference callset with `lifted + rejected`; any difference is reported explicitly. Reject-rate interpretation must use the liftover candidate set, not all gVCF records or reference-confidence blocks.

After liftover, candidate mode also scans the produced variant VCF and requires zero `<*>` and zero `<NON_REF>` ALT records. The JSON report records source/target REF-validation success, TBI creation, placeholder counts, candidate conservation, and reject FILTER/reason/contig summaries.

## CrossMap

CrossMap is **not a runtime dependency** and is not the authoritative mapping engine. This keeps the portable application free of a Python runtime and avoids two competing production liftover semantics.

CrossMap is useful as a differential test oracle for uncomplicated loci. When BCFtools/liftover and CrossMap disagree, the disagreement is investigated against the chain, source/target reference, and allele representation. Majority vote is not proof.

## positions.csv / lifted_positions.csv

These files are not required by the application.

A trusted mapping table can be added under `testdata/validation/` with a schema such as:

```text
source_chrom,source_pos,source_ref,source_alt,target_chrom,target_pos,target_ref,target_alt,provenance
```

A `lifted_positions.csv` generated by CrossMap is comparison/regression data, not ground truth merely because it came from another liftover program.

## Release validation corpus

The release gate should contain:

- forward/reverse-strand SNPs;
- REF/ALT swaps;
- insertions/deletions and reverse-strand indels;
- multi-allelic records;
- X/Y and separately-reviewed mitochondrial cases;
- chain gaps/unmappable records;
- loci near assembly-specific indels;
- UCSC and GRCh chromosome naming;
- GATK single-sample gVCF -> GenotypeGVCFs -> liftover fixtures;
- DeepVariant `<*>` fixtures that verify `GT="alt"` extraction, `<*>` trimming, retention of sequence-resolved `TYPE=OTHER` complex calls, and exclusion of `RefCall`/`NoCall` records;
- explicit candidate-mode fixtures for `<NON_REF>`/`<*>` inputs;
- corrupt/truncated input, cancellation, and partial-output cleanup;
- engine-bundle corruption/re-extraction tests.

## Real-data release gates

Results recorded through v1.2.0-dev on the reference WSL2 machine (engine: embedded bcftools 1.24, score `e10b2e56cfbe`):

1. **DeepVariant gVCF, private cohort sample (`deepvariant_star`)** — 50,574,105 input records, 5,422,963 candidates: 4,942,650 lifted (91.143%), 480,313 rejected (8.857%), exact candidate conservation, source/target REF validation, TBI and placeholder checks all passing. The identical run was repeated with the v0.9.0 release build and reproduced the same counts bit-for-bit (58m11s end-to-end).
2. **Ordinary VCF, GIAB HG002 v4.2.1 (GRCh38 benchmark)** — 4,048,342 input records, `variant_vcf` mode: 4,043,367 lifted (99.88%), 4,975 rejected (0.12%; UnmappedAnchors 4,929, MismatchAnchors 43, ApartAnchors 3), source/target REF validation and TBI passing (5m17s). Independent cross-check: after left-aligned normalization, the lifted output shares 4,044,418 of 4,091,631 records (**98.85%**) with the official GIAB GRCh37 v4.2.1 benchmark VCF (which itself shares 99.09% of that benchmark); the remaining ~1% consists of single SNPs/indels near chain-edge and representation-difference regions.

3. **GATK gVCF, `gatk-test-data` HG00187 reblocked exome gVCF (hg38, GATK-produced)** — 2,977,065 gVCF records; the pinned runtime (Temurin JRE 17.0.20.1 + GATK 4.7.0.0) was downloaded, installed and executed in the same run; GenotypeGVCFs then liftover produced 71,370 variants with 479 rejects (0.67%), source/target REF validation, TBI and placeholder checks passing (2m24s including runtime download).

4. **Target naming profile gate, GIAB HG002 v4.2.1 GRCh38 → `grch37-primary` (post-v1.0.0)** — same input as gate 2 (4,048,342 records): 4,043,025 lifted into GRCh37 primary naming; liftover rejects identical to the ucsc-hg19 baseline (4,975); 342 records that lifted to non-primary contigs were dropped into the `non_primary_contig` profile bucket (chrM is absent from this 1–22 benchmark). The output header carries the GRCh37 primary dictionary (25 contigs, MT=rCRS 16,569) and `##vcflift_target_profile=grch37-primary`. Cross-check: after left-aligned normalization against GRCh37 primary sequence with contig names reconciled, the profiled output matches **3,997,316 of the official GRCh37 v4.2.1 benchmark's 4,033,796 normalized records (99.10%)** exactly; 98.87% of the profiled output is covered by the benchmark. Independent sequence-identity evidence: `bcftools norm` reported **zero REF mismatches** for both the profiled output and the official benchmark against a GRCh37-named copy of the hg19 primary sequence (4.04M + 4.03M records), confirming GRCh37 primary ≡ UCSC hg19 primary sequence for 1–22/X/Y.

5. **Reverse direction gate, GIAB HG002 v4.2.1 GRCh37 → hg38 (post-v1.0.0)** — input in GRCh37/hs37d5 naming (4,033,796 records), detected as hg19 by majority contig-length vote (hs37d5 MT carries the rCRS length, which collides with hg38 MT; 1–22/X/Y lengths break the tie); contigs renamed to UCSC via the hg19 chromAlias map; source REF validation against hg19 passed with zero mismatches (a third independent confirmation of GRCh37 ≡ hg19 primary sequence): 4,033,574 lifted (99.994%), 222 rejected (UnmappedAnchors 213, MismatchAnchors 8, ApartAnchors 1), target REF validation against hg38 and TBI passing (1m58s). Cross-check: after left-aligned normalization against hg38, the reverse output matches **3,997,338 of the official GRCh38 v4.2.1 benchmark's 4,048,342 normalized records (98.74%)** exactly; 99.10% of the reverse output is covered by the benchmark — the same ~1% chain-edge/representation error budget as the forward gates. Per-locus inverse consistency was verified in both directions on real sequence (hg19 chr1:1,000,001 ↔ hg38 chr1:1,064,621).

6. **Target naming profile gate, GIAB HG002 v4.2.1 GRCh37 → `grch38-primary` (v1.2.0-dev)** — same input as gate 5 (4,033,796 records, reverse hg19 → hg38): 4,033,381 lifted into GRCh38 primary naming; liftover rejects identical to the ucsc-named reverse baseline (222); 193 records that lifted to non-primary contigs were dropped into the `non_primary_contig` profile bucket (4,033,381 + 193 = 4,033,574, the baseline lifted count — profile drops never masquerade as liftover rejects). chrM carries over as MT: hg38 chrM is the rCRS, sequence-identical to the GRCh38 MT, so there is no stale-chrM bucket on this side. The output header carries the GRCh38 primary dictionary (25 contigs, MT=rCRS 16,569) and `##vcflift_target_profile=grch38-primary`; the dictionary matches the official benchmark's GRCh38 primary dictionary name-for-name and length-for-length (M/MT alias reconciled). Name equality is not the gate: after renaming the output back to UCSC names and left-aligned normalization against the managed hg38 FASTA, the profiled output matches **3,997,338 of the official GRCh38 v4.2.1 benchmark's 4,048,342 normalized records (98.74%)** exactly — the identical shared count as gate 5, confirming the profile changes naming only; 99.11% of the profiled output is covered by the benchmark. Independent REF evidence: `bcftools norm -c e` against hg38 reported **zero mismatches** over all 4,033,381 records. The conversion ledger's first real-data pass ran in the same conversion: 35,372 `unchanged` + 41 `same_locus_allele_swap` + 3,973,196 `position_shift` + 24,772 `unclassifiable` (`left_align_representation_change` reserved, zero, as designed) = 4,033,381 = `lifted_variants`; the sidecar copied `plugin_flip` on 3,976 and `plugin_swap` on 21,215 records verbatim (docs/LEDGER.md). Ledger scale observation from the same run: the gz sidecar for 4,033,381 records is 39.7 MB (~9.9 bytes/record compressed), written as one streaming pass over the finalized output; end-to-end conversion time including the ledger pass was 19m12s on the reference machine. The v1.0.0 DeepVariant cohort input (50.6M records) is no longer on disk; a cohort-scale ledger re-observation is deferred until that private input is provided again — the 4.03M-record benchmark run above is the recorded real-data evidence.

## Certificate verification (v1.2.0-dev)

The user-FASTA dictionary certificate was exercised on real files (docs/CERTIFICATE.md): an hg19-derived GRCh37-named FASTA (contig `M` carrying the old NC_001807 at 16,571 bp plus an appended rCRS `MT` copy) under `grch37-primary` returns **incompatible**, first reason "MT length 16571 is the old NC_001807 sequence (hg19 chrM); this dictionary carries the rCRS MT (16569)", with 24/25 contigs matched, the duplicate MT listed among extras, the conversion completing with all outputs written, and the CLI exiting code 3 with the fixed state sentence. A synthetic exact-dictionary FASTA returns **compatible** with the fixed compatible sentence (unit tests cover missing/decoy/EBV/other-extra reasons and alias normalization end to end).

## Engine validation

Every native bundle is self-describing. Build CI must prove that:

```text
bcftools --version
bcftools plugin -l        contains liftover
bcftools +liftover -h     contains required options
```

The generated manifest records SHA-256 for every bundled file. Release builds require a pinned `freeseek/score` ref rather than silently following `master`.
